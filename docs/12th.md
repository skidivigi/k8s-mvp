# Двенадцатый шаг: Cilium и NetworkPolicy

На этом шаге мы заменим стандартный сетевой плагин kind на **Cilium**, разберем базовую архитектуру сети Kubernetes и применим настоящие `NetworkPolicy` между Pod.

До этого урока лаборатория работала на стандартном CNI kindnet.

В двенадцатом уроке кластер пересоздается:
kindnet отключается, а вместо него устанавливается Cilium. Необходимо раскоментировать **8-9** строчки в [kind cluster](../kind/cluster.yaml)

Все последующие уроки выполняются уже на кластере с Cilium.

Главная цель урока:

```text
kind без стандартного CNI
        ↓
Cilium как CNI
        ↓
Pod-to-Pod сеть
        ↓
NetworkPolicy
        ↓
eBPF-фильтрация
        ↓
Hubble observability
```

После урока будет работать следующая схема:

```text
network-client ─────► network-backend  ✅

network-stranger ───► network-backend  ❌

network-client ─────► CoreDNS          ✅

network-client ─────► интернет         ❌
```

# 3. Что такое CNI

CNI расшифровывается как:

```text
Container Network Interface
```

Kubernetes сам не создает сетевые интерфейсы Pod и не назначает им IP-адреса.

Упрощенная цепочка запуска Pod:

```text
kubelet
   ↓
container runtime
   ↓
CNI plugin
   ↓
создание сетевого интерфейса
   ↓
назначение IP
   ↓
добавление маршрутов
   ↓
Pod подключен к сети
```

CNI отвечает за:

```text
выдачу IP-адресов Pod;
маршрутизацию между Pod;
связность между Node;
интеграцию с сетью Linux;
исполнение NetworkPolicy — если CNI их поддерживает.
```

---

# 4. kindnet и Cilium

По умолчанию kind устанавливает простой сетевой компонент:

```text
kindnetd
```

Он подходит для базовых лабораторий, но для этого урока мы отключаем встроенный CNI и устанавливаем Cilium.

Cilium будет отвечать за:

```text
Pod networking;
маршрутизацию;
сетевые identity;
NetworkPolicy;
eBPF datapath;
Hubble observability.
```

Важно:

```text
NetworkPolicy — объект Kubernetes.

Cilium — компонент, который реально исполняет эту политику.
```

Схема:

```text
kubectl apply NetworkPolicy
            ↓
Kubernetes API Server
            ↓
объект NetworkPolicy
            ↓
Cilium Agent
            ↓
eBPF-программы
            ↓
Linux Kernel
            ↓
ALLOW или DROP
```

---

# 5. Что такое eBPF

eBPF позволяет загружать небольшие проверяемые программы в ядро Linux.

Для нашего урока достаточно понимать следующую модель:

```text
сетевой пакет
      ↓
Linux Kernel
      ↓
eBPF-программа Cilium
      ↓
проверка identity, направления и порта
      ↓
FORWARDED или DROPPED
```

Cilium использует eBPF для обработки сетевого трафика, применения политик и сбора наблюдаемости.

# 6. Изменение `kind/cluster.yaml`

В существующий файл `kind/cluster.yaml` нужно добавить:

```yaml
networking:
  disableDefaultCNI: true
```

Полный пример:

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4

name: platform-lab

networking:
  disableDefaultCNI: true

nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"

    extraPortMappings:
      - containerPort: 80
        hostPort: 80
        protocol: TCP

      - containerPort: 443
        hostPort: 443
        protocol: TCP

  - role: worker

  - role: worker
```

Ключевой блок:

```yaml
networking:
  disableDefaultCNI: true
```

Он говорит kind:

```text
не устанавливать kindnetd;
создать Kubernetes-кластер без готовой Pod-сети;
ожидать, что CNI будет установлен отдельно.
```

# 8. Установка Cilium CLI

```makefile
# 12th lab - Cilium + NetworkPolicy

CILIUM_VERSION=1.19.6
NETWORK_DIR=k8s/11-cilium-network-policy

.PHONY: install-cilium-cli-12
install-cilium-cli-12:
	@set -e; \
	CILIUM_CLI_VERSION=$$(curl -s https://raw.githubusercontent.com/cilium/cilium-cli/main/stable.txt); \
	CLI_ARCH=amd64; \
	if [ "$$(uname -m)" = "aarch64" ]; then CLI_ARCH=arm64; fi; \
	curl -L --fail --remote-name-all \
		https://github.com/cilium/cilium-cli/releases/download/$${CILIUM_CLI_VERSION}/cilium-linux-$${CLI_ARCH}.tar.gz{,.sha256sum}; \
	sha256sum --check cilium-linux-$${CLI_ARCH}.tar.gz.sha256sum; \
	sudo tar xzvfC cilium-linux-$${CLI_ARCH}.tar.gz /usr/local/bin; \
	rm cilium-linux-$${CLI_ARCH}.tar.gz{,.sha256sum}; \
	cilium version --client
```

```bash

```

# 20. Что такое NetworkPolicy

`NetworkPolicy` — стандартный объект Kubernetes:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
```

Он описывает разрешенный трафик для выбранных Pod.

Основные поля:

```yaml
spec:
  podSelector:
  policyTypes:
  ingress:
  egress:
```

---

# 21. podSelector

`podSelector` выбирает Pod, к которым применяется политика.

Пример:

```yaml
podSelector:
  matchLabels:
    app: network-backend
```

Это означает:

```text
политика защищает Pod с label app=network-backend
```

Пустой selector:

```yaml
podSelector: {}
```

означает:

```text
выбрать все Pod текущего namespace
```

# 22. Ingress и Egress

Ingress отвечает на вопрос:

```text
кто может подключиться к этому Pod?
```

Схема:

```text
client ─────► backend
             ▲
             │
          Ingress
```

Egress отвечает:

```text
куда этот Pod может подключаться?
```

Схема:

```text
client ─────► backend
  │
  └── Egress
```

Если обе стороны изолированы, для соединения должны быть разрешены:

```text
Egress клиента
      +
Ingress backend
```

# 27. Как складываются NetworkPolicy

Политики не обрабатываются сверху вниз.

Нет модели:

```text
первая политика победила;
последняя политика победила.
```

Разрешения применимых политик объединяются.

У нас есть:

```text
deny-backend-ingress
+
allow-client-to-backend
```

Результат:

```text
backend изолирован;
разрешен только явно описанный client → backend:80.
```

# 29. Почему ломается DNS

При обращении:

```bash
curl http://network-backend
```

сначала выполняется DNS-запрос:

```text
network-backend
       ↓
CoreDNS
       ↓
ClusterIP Service
```

После `deny-client-egress` клиент не может обратиться к CoreDNS.

Поэтому ошибка может выглядеть так:

```text
Could not resolve host: network-backend
```

# 30. Разрешаем DNS

Создаем:

```text
k8s/11-cilium-network-policy/04-allow-client-dns.yaml
```

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: allow-client-dns
  namespace: lab

spec:
  podSelector:
    matchLabels:
      app: network-client

  policyTypes:
    - Egress

  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system

          podSelector:
            matchLabels:
              k8s-app: kube-dns

      ports:
        - protocol: UDP
          port: 53

        - protocol: TCP
          port: 53
```

Здесь `namespaceSelector` и `podSelector` находятся в одном элементе `to`.

Это означает логическое `AND`:

```text
Pod находится в kube-system
И
имеет label k8s-app=kube-dns
```

Добавляем:


# 35. Labels и identity

IP Pod непостоянный.

После пересоздания:

```text
старый backend IP: 10.244.1.15

новый backend IP: 10.244.2.9
```

Поэтому Cilium опирается не только на IP, но и на identity, сформированную из labels.

Например:

```yaml
labels:
  app: network-backend
  role: backend
```

Схема:

```text
Pod labels
    ↓
Cilium Security Identity
    ↓
Policy decision
```

Это позволяет политикам продолжать работать после пересоздания Pod.

# 49. Что важно запомнить

```text
Kubernetes сам не создает сеть Pod.

Для сети используется CNI.

kind по умолчанию использует kindnetd.

disableDefaultCNI отключает встроенный CNI kind.

Cilium применяет NetworkPolicy.

Cilium использует eBPF.

NetworkPolicy — декларация Kubernetes.

Ingress контролирует входящий трафик.

Egress контролирует исходящий трафик.

podSelector выбирает защищаемые Pod.

from определяет разрешенные источники.

to определяет разрешенные назначения.

ports ограничивает протоколы и порты.

Для DNS после deny egress нужно отдельное правило.

Разрешения разных NetworkPolicy объединяются.

Hubble показывает разрешенные и заблокированные flows.
```

# Итог

До этого урока сеть Kubernetes могла выглядеть как скрытая магия:

```text
Pod получают IP;
Service доставляет трафик;
все Pod могут общаться.
```

После урока цепочка становится понятной:

```text
kind создает кластер без стандартного CNI;

Cilium подключает Pod к сети;

Cilium создает endpoints и identities;

NetworkPolicy описывает разрешенный трафик;

Cilium превращает политики в eBPF-правила;

Linux Kernel разрешает или отбрасывает пакеты;

Hubble показывает результат.
```

Финальная модель:

```text
network-client
       ├── DNS:53 allowed
```
